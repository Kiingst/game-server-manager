Yes—this is feasible as a CS project, especially if you target Linux, Docker, and a small initial set of games. The important design change is to avoid trying to express every difference through class inheritance.
Python and Flask are not the problem. Keep them unless you have a specific reason to switch. Your time is better spent improving the architecture than rewriting the application in another language or framework.
Recommended architecture
Split the system into four conceptual parts:
Web interface
     ↓
Backend API and task manager
     ↓
Game-specific adapters
     ↓
One container per server instance
1. Web interface
The frontend can provide:
A list of installed server instances, grouped by game
Start, stop, restart, and update actions
Server status and resource usage
Live console output
Command entry
Connected-player information
Configuration editing
Backups and log viewing
Use normal HTTP requests for actions and WebSockets or Server-Sent Events for live console output and status changes.
2. Backend
The backend should manage server instances, but it should not contain Minecraft-specific logic.
Its common responsibilities would include:
Creating and controlling containers
Tracking server states
Validating user actions
Managing files and directories
Streaming logs
Running backups
Recording events
Calling the appropriate game adapter
Server actions should be asynchronous. Starting or updating a large server could take minutes, so a web request should create a job instead of remaining open until the operation finishes.
A useful state model is:
STOPPED → STARTING → RUNNING → STOPPING → STOPPED
                  ↘ ERROR ↗
This prevents problems such as clicking “Start” five times or trying to update a running server.
3. Game adapters
The biggest lesson from your Minecraft implementation is correct: game servers behave differently. A purely generic Server class will eventually fill up with game-specific conditions.
Use a small common interface instead:
class GameAdapter:
    def install(self, instance): ...
    def update(self, instance): ...
    def start(self, instance): ...
    def stop(self, instance): ...
    def send_command(self, instance, command): ...
    def get_players(self, instance): ...
    def get_status(self, instance): ...
Minecraft, Valheim, Terraria, and other games can implement this interface differently.
The main server instance can then contain an adapter rather than inherit all its behavior from it:
server = ServerInstance(
    name="Survival",
    game="minecraft",
    adapter=MinecraftAdapter(...)
)
This composition-based approach will be easier to maintain than a deep hierarchy such as Server → JavaServer → MinecraftServer → ForgeServer.
4. Game definition files
A declarative game file is a very good idea, but it cannot handle every difference. Use configuration for predictable differences and Python adapters for complicated behavior.
A simplified definition might look like:
id: minecraft-java
display_name: Minecraft Java

container:
  image: itzg/minecraft-server
  ports:
    - container: 25565
      protocol: tcp
  data_directory: /data

startup:
  command: []
  ready_log_pattern: 'Done \([0-9.]+s\)!'
  shutdown_command: stop
  startup_timeout: 180

console:
  method: rcon
  port: 25575

players:
  method: rcon
  command: list

configuration:
  files:
    - path: server.properties
      format: properties

environment:
  MEMORY:
    type: string
    default: 2G
  EULA:
    type: boolean
    required: true
A Valheim definition could specify command-line arguments and a query protocol instead. Terraria might use console input and log parsing.
This gives you three levels:
Generic engine: containers, jobs, logs, users, backups
Game definition: ports, image, settings, commands and file formats
Optional adapter: unusual installation, player lookup or shutdown logic
That hybrid model is probably the strongest part of the proposed design.
Should you replace Flask?
Probably not.
Flask is sufficient for:
A REST API
Authentication
A database-backed application
Docker control
WebSocket support through an extension
FastAPI would provide convenient type validation, asynchronous endpoints, and generated API documentation. It is a reasonable option if the existing Flask code is small, but it will not solve the difficult game-management problems. If you already have meaningful Flask code, keep Flask for the first version.
Likewise, the frontend can initially use Flask templates with a little JavaScript. React, Vue, or another frontend framework can be added later if the interface becomes complex.
What can and cannot be standardized
Highly standardizable:
Container lifecycle
CPU and memory limits
Port mappings
Files and persistent volumes
Logs
Backups
Environment variables
Status history
Scheduled restarts
Permissions
Partially standardizable:
Configuration files
Installation and updates
Graceful shutdown
Readiness detection
Console commands
Player lists
Usually game-specific:
SteamCMD installation details
Authentication tokens
Mod loaders
Query and remote-console protocols
Save-file formats
Update compatibility
Detecting when the game is genuinely ready
Translating configuration values into command-line arguments
Some games will not expose a reliable player list or remote console. The UI should represent unsupported features rather than pretending every adapter has every capability:
{
  "console": true,
  "player_list": false,
  "live_metrics": true,
  "mods": false,
  "graceful_shutdown": true
}
A realistic project scope
A strong CS-project MVP would support:
Linux as the host operating system
Docker as the only runtime
One administrator account
Minecraft Java plus one substantially different game
Create, start, stop, and restart
Persistent game data
Live logs and console commands
Basic configuration editing
Player information where supported
Backup creation and restoration
Supporting “most games” should be treated as the long-term direction, not the first deliverable. Demonstrating that a third game can be added primarily through a definition file would be a very good measure of architectural success.
Important risks
The largest risk is security. A backend with access to the Docker socket can effectively control the entire host. Do not expose this application directly to the internet during development. Validate paths, commands, port numbers, uploaded files, environment variables, and container settings.
Also distinguish these operations clearly:
Restart: stop and start while preserving data
Reset: delete or replace the world/save data
Reinstall: replace server software while normally preserving data
“Reset” should require confirmation and ideally create a backup first.
Overall, the idea is sound. Keep Python, probably keep Flask, replace heavy inheritance with adapters plus declarative game definitions, and limit the first version to two games. That would produce a feasible project while still demonstrating a design capable of expanding much further.
